---
title: In the Godot editor
description: Check the project, see its problems on the right lines, format scripts, and run tests without leaving Godot.
---

GDSuite comes with an addon for the Godot editor. It runs the same checks as
`gdsuite check`, with the same `gdsuite.toml`, so what is green in the editor
is green in the terminal and in CI.

## Turn it on

The first `gdsuite test` (or `gdsuite init`) puts the addon in
`addons/gdsuite/`. Commit it with the rest of the project. Then, once:

1. Open the project in Godot.
2. Go to **Project → Project Settings → Plugins** and turn on **GDSuite**.

The addon runs the `gdsuite` program you installed: it finds the one in your
project's `.gdsuite/` folder, or on your `PATH`. If it says gdsuite is not
found, see [Install](/install), or set its path in **Editor Settings →
GDSuite → Program**.

It works best with Godot 4.7 and newer; Godot 4.5 is supported.

## Check the project

Two icons in the editor's top bar show where the project stands:

- **Check** (a page with a tick): grey until GDSuite has looked at the
  project, then red when there are errors, yellow when there are only
  warnings, green when there are none. It counts what formatting, linting,
  the compile check and code health found, as listed in the Problems dock.
  Click it to check the project; it does what **Check** in the Problems dock
  does.

- **Tests** (a flask): red when a test fails, green when the tests that ran
  pass, grey before any test ran. Click it to run all tests, or to stop them
  while they run; it does what **Test all** in the Tests dock does.

Each icon says two things apart: what the last check or run found, and
whether that still holds for your code as it is now.

| The icon | Means |
| --- | --- |
| Grey, no badge | Nothing known yet: not checked, or no test ran |
| In colour, with a badge: ✓ green, ! yellow, × red | What the last check or run found, and it is up to date |
| The same, faded | What it found before your last changes: a file changed since (saved, edited, or changed outside the editor), or some tests have not run since their scripts changed. Check, or run the tests, to bring it up to date |
| A spinner over it | A check or a run is going; the faded colour is what the last one found. While tests run, the flask becomes **Stop** |

The badge's shape says the result as well as its colour, for those who don't
tell red, yellow and green apart. Hover an icon for the same in words: "2
errors, 1 warning · Out of date: 3 files changed since". The **Check** and
**Test all** buttons of the docks, and the icons before the docks' names,
show the same.

### What Check does

1. With **Autofix** on (the default), it fixes what can be fixed safely:
   it formats the scripts, and applies the lint fixes that can't change what
   the code does (see [what can be fixed](/linting#what-can-be-fixed)).
   Scripts with unsaved changes are left as they are, and the editor shows
   the scripts it changed as they are now.
2. It checks what is left, with the tools a check covers: **Format**,
   **Lint**, **Compile** and **Health**, all on by default.

The same Autofix applies when saving checks a script (see [when you
save](#when-you-save)). Turn it off, or leave a tool out of the check, in the
**⚙** menu of the Problems dock. A tool left out has no filter in the Problems dock, and its
problems aren't listed.

## The Problems dock

The **Problems** dock lists what [formatting](/formatting),
[linting](/linting), the [compile check](/type-checking) and [code
health](/code-health) found, by script:

```text
⚠  1 script not formatted  ·  double-click to format it
v player/player.gd    1 ×  ·  1 ⚠  ·  not formatted
   ⚠   8  The local variable "dir" is declared but never used…   unused-variable · compile
   ×   9  Identifier "sped" not declared in the current scope.                 compile
v enemies/glow.gdshader    1 ×
   ×   4  Invalid arguments for the built-in function: "vec4(float,float,float)".  compile
```

The script you're editing comes first, then the scripts with errors, then the
others. Click a script to fold or unfold its problems. The button next to
**Current** folds them all, and once all are folded, unfolds them all. Each
problem says:

- whether it's an **error** or a **warning**: its line is red (×) or
  yellow (⚠);
- its **line**, and the column when the tool knows it;
- the **message**;
- its **code** and the **tool** that found it. The code is the lint rule
  (`max-line-length`) or the name of Godot's warning (`unused-variable`,
  which is `UNUSED_VARIABLE` in Project Settings). Godot's errors have no
  name, so only the tool is shown. The tool is `format`, `lint`,
  `compile` (Godot's own compiler, which also reads shaders, scenes and
  resources), or `health`.

Scripts that formatting would change are one row at the top: double-click it
to format them all (scripts with unsaved changes are left as they are). A
script listed for other problems also says it is "not formatted".

### Find your way

- **Alt+F8** opens the next problem after the caret, and **Shift+Alt+F8** the
  one before, in the order of the list, around its end. Not F8, as in VS
  Code: Godot uses it to stop the running project. Change them in **Editor
  Settings → Shortcuts**; the command palette has **Next Problem** and
  **Previous Problem**.
- **Double-click** a problem to open the script at its line.
- **Select** a problem to see, in the details under the list, all of its
  message, what its code means, and buttons for what can be done: **Open**, **Fix** (a lint
  problem that can be fixed), **Ignore on this line**, **Turn off** its rule
  for the whole project (written in `gdsuite.toml`), **What does it mean?**,
  and **Copy**. **Right-click** shows the same actions. Click on empty space,
  or press **Escape**, to select nothing.
- Hover a problem for its **copy** button: it copies it as a compiler prints
  it, `enemies/math.gd:5: warning[integer-division]: … (compile)`.

### Filter

The filters look like the Output dock's: one that is on has a background,
one that is off is faded.

- The error and warning icons count what the project has (hover one for its
  name), and hide or show those problems.
- **Format**, **Lint**, **Compile** and **Health** count what each tool found, errors in
  red and warnings in yellow, and hide or show its problems. While a tool
  checks, a spinner turns next to its name.
- **Project | Current**: the whole project, or only the script you're
  editing. The one not chosen is faded.

### Is it up to date?

- The bar says when the last check reported, in minutes: "Checked &lt;1 min
  ago", "Checked 3 min ago".
- A script you edited since it was checked has its problems faded, and says
  "edited since checked", until it's checked again when you save.
- **Check** looks at the whole project again, and fixes what it can (see
  [what Check does](#what-check-does)).
- The icon before the dock's name says where the project stands, as the
  top bar's Check icon does: a red ×, a yellow ! or a green ✓, faded when
  files changed since, a spinner while a tool checks, and a grey dot before
  the first check.
- The compile check and code health look at the whole project at once: a
  file saved or changed since they ran makes all they found out of date, not
  only that file's. Files changed outside the editor, by a checkout, a pull
  or another editor, count once the editor sees them; nothing runs for them
  until you check.

When the dock is narrow, its buttons go on two lines rather than widening
the bottom panel.

### The details

The details of the selected problem are under the list. The buttons in
their corner fold them to one line, which still says what is selected (click
it to unfold them), and put them beside the list, or back under it. The Tests
dock's details do the same. Both are kept for the project.

Drag the edge of the **Line** or **Code and tool** column to resize it;
**⚙ → Columns** shows or hides each column and resets the widths. Both are
kept for the project.

The list shows the whole project, including problems in scripts you haven't
opened: a broken reference in a scene, a script loading a file that was
renamed. For a syntax error, Godot reports only the first one of a script,
where the script editor also lists the errors that follow from it: fix the
first and save.

Like any dock, you can move it to a side, or make it a window of its own.

### Code health and the graph

Code health findings are listed with the other problems: a function too long
or too complex, a script too big, scripts that use each other in a cycle.
Critical findings are errors, the others warnings. They don't fail
`gdsuite check` unless the project says so (see [the check](/check#code-health)).
A finding that a lint rule also reports, on the same line, is listed once,
as the lint problem. Select a finding for what it means, the scripts it
involves, and **What to do**, with the place to start: "line 122: a match
with 16 branches", or "lines 130–162: this for block is 33 lines. It could
be a function of its own". Click a line to go to it.

**List | Graph** switches the list for a graph of which script uses which:
the scripts that use others on the left, what they use on the right, arrows
in red where they make a cycle. Each script shows how many problems it has,
in their colour. With **Current**, the graph shows the script you're editing,
the scripts that use it and those it uses.

- Scroll to zoom, drag to move. Double-click empty space to see it all.
- Click a script to see, in the details, what it uses and what uses it, and
  how: it extends it, preloads it, uses its class name, uses it as an
  autoload, or through a scene. Double-click it to open it.
- A health problem's **Show in the graph** selects its script there.

Health in the editor is a quick look: it skips what needs Git history.
**⚙ → Open the full health report** runs [`gdsuite health`](/code-health) and
opens its report in your browser: what to fix first, ordered by how often
each script changes, with a guide to each kind of finding.

## Problems in the script editor

In the script you're editing, a line with a problem gets a red × or a yellow
⚠ in the margin and a light tint of the same colour. Click the mark to read the problem.

## Format a script

**Format script** formats the script you're editing, with the project's
[formatting settings](/reference/formatting-style), even before you save it.
It's one step to undo with **Ctrl+Z**.

Run it from:

- **Project → Tools → GDSuite → Format script**,
- the command palette (**Ctrl+Shift+P**, then "Format Script"),
- **Shift+Alt+F**, which you can change in **Editor Settings → Shortcuts**.

A script with a syntax error is left as it is.

## Run tests

The **Tests** dock lists the project's tests: the ones `gdsuite test` runs,
from the folder in `[commands] default_test_target`.

- **Test all** runs every test; while tests run, it becomes **Stop**. The
  flask in the top bar does the same.
- **Test failed** runs again the tests that failed, and says how many.
- Hover a row for its **▶**: it runs that script or that test.
  **Right-click** runs the selected tests, and **double-click** opens a test.
  Click on empty space, or press **Escape**, to select nothing.
- With **⚙ → Tests → On save** on, saving a script, a scene or a resource
  runs the tests again:
  only the tests that use it, directly or through other scripts, scenes and
  resources (`extends`, `preload`/`load`, `class_name`, autoloads), and the
  scenes they were seen loading when they last ran. A test script runs its own
  tests; a change to `project.godot` or an autoload runs them all. See [what a
  change affects](https://q-rault.github.io/gdtest/docs/running-tests#only-what-your-change-affects).
  It doesn't run tests for nothing:
  - It waits for your saves to stop for a moment, so several saves in a row
    make one run.
  - A save while tests run stops that run, which runs code that has changed
    since, and starts another: the tests the save affects, and those the
    stopped run had yet to finish.
  - When the script you saved doesn't compile, its tests wait, and the bar
    says "Waiting for hud.gd to compile": they could only fail to load. They
    run once the check after a save finds it compiles (with **⚙ → Check →
    On save** on in the Problems dock; off, they run at once).
  - When you save a script back to what it was when its tests last ran, say
    after renaming a variable and renaming it back, nothing runs: its tests
    are up to date again.
- **Search tests** keeps the tests whose name or script matches.
- The ✗ (in red), ✓ (in green) and clock icons count the tests that failed,
  passed, and are to run (hover one for its name); click one to hide those
  tests, or show them again, as in the Problems dock. "To run" are the tests
  not run yet, and those whose scripts changed since they ran.
- Select a test that failed to read why, under the list: what each assertion
  expected and got, **at** which line (click it to open the script there),
  that line of code, and the test's local variables then. Click the test's
  name to open it. To see the local variables, turn on **Project Settings →
  Debug → GDScript → Always Track Local Variables**; see [reading a
  failure](https://q-rault.github.io/gdtest/docs/running-tests#reading-a-failure).

While tests run, a bar under the buttons fills, green, or red once a test
failed, and the bar shows where the run is (`120/358 · 4.2 s`).
Each test shows where it is: a clock while it waits, a spinner while it runs,
then its result. A test that failed is red; a test that has not run, or
whose script changed since it ran, is faded. After a run, the scripts with a
test that failed are unfolded. Otherwise the list keeps its order, and what
you unfolded stays unfolded; click a script to fold or unfold it, or fold
them all, and unfold them all, with the button next to the search. When a save
starts a run, the bar says why: "affected by hud.gd". The icon before the
dock's name is the top bar's flask badge: a red × when a test failed, a green
✓ when the tests that ran pass, faded while some are to run, a grey dot before
any test ran. A file changed outside the editor makes the tests it affects
to run, without running them.

The **Time** column shows how long each test took, and each script the time
of its tests; under a millisecond, nothing. Click its title to put the
slowest first, and the **Test** title to sort by name again. Drag its edge to resize it.

In the script editor, a test script gets a ▶ next to each test. Click it to
run that test; after a run, it shows whether the test passed. Folders and
scripts in the **FileSystem** dock have **Run Tests** in their right-click
menu.

The command palette has **Test All**, **Rerun Failed Tests** and **Run
Tests in Script**.

Tests run in the background with the Godot of your editor, as `gdsuite test`
runs them, so they don't stop you from working. They run in parallel: one
Godot per processor core, each taking the next test waiting.

If you used the gdtest panel before (`addons/gdtest_editor/`), `gdsuite test`
removes it: the Tests dock replaces it. If you changed its files, they are kept
and you can delete the folder.

## When you save

Each dock's **⚙** menu has an **On save** setting: on, saving does what the
dock's main button does, on what you saved.

- **Check → On save** (Problems dock): saving a script checks it again, and
  a moment later compiles it with the scripts, scenes and resources that use
  it, and measures the project's health, in the background. Saving a scene
  or a resource does the same. With **Autofix** on, the same setting as for
  **Check**, the script is fixed and formatted first. The compile check runs
  on the whole project when `project.godot` changed, or when the save
  reaches more than half the project (compiling part of it only answers
  sooner, and past half not by much), and again after 30 seconds without a
  save, for what the links between files don't show (a `class_name` removed
  that other scripts still use).
- **Check → Lint as you type** (Problems dock): the script you're editing is
  linted as you type, a moment after you stop, before you save. Its lint
  problems are up to date in the list and in the script editor; the other
  tools' problems stay faded until you save. While the text doesn't parse,
  the last problems found stay.
- **Tests → On save** (Tests dock): saving a script, a scene or a resource
  runs the tests it can affect.

The settings of the **⚙** menus:

| Dock | Setting | Default | What it does |
| --- | --- | --- | --- |
| Problems | Check → Autofix | On | A check formats the scripts, and applies the safe lint fixes, first: the project's on **Check**, the saved script's on save |
| Problems | Check → On save | On | Saving a script checks it, and what it affects a moment later |
| Problems | Check → Lint as you type | On | The script you're editing is linted before you save |
| Problems | A check covers → Format, Lint, Compile, Health | On | The tools a check runs, and whose problems are listed |
| Problems | Show → Problems in the script editor | On | The icons and tints in the script editor |
| Problems | Show → Check in the top bar | On | The Check icon in the editor's top bar |
| Tests | Tests → On save | Off | Saving runs the tests it can affect |
| Tests | Show → Test all in the top bar | On | The flask in the editor's top bar |

They are also in **Editor Settings → GDSuite**. These are yours: they apply
to every project on your computer.

### The same choice for the whole team

To make everyone run the affected tests on save, say so in the project's
`gdsuite.toml`:

```toml
[editor]
test_on_save = true
```

A setting in `[editor]` wins over each person's own; the ⚙ menu shows it as
"set by this project". The keys are `autofix`, `check_format`, `check_lint`,
`check_compile`, `check_health`, `check_on_save` and `test_on_save` (see
[gdsuite.toml](/reference/gdsuite-toml)). The keys of GDSuite 0.7 and earlier
still count: `lint_on_save` and `type_check_on_save` for `check_on_save`,
`format_on_save` for `autofix`, `run_tests_on_save` for `test_on_save`.

## Your changes to the addon

`gdsuite` updates `addons/gdsuite/` when you update gdsuite. A file of the
addon you changed is kept as it is: delete it to get the new version. A kept
file may not work with the new version of the others, so `gdsuite setup` and
`gdsuite doctor` name it.

`addons/gdsuite/files.sha256` holds the hash of each file as `gdsuite` wrote
it, which tells your changes from another version's files. Commit it with the
addon, so that a fresh clone or a CI job can update it too.
