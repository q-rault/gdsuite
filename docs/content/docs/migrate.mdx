## What this page is for

This page explains how to bring an existing repository onto the current `gdsuite` config and workflow contract.

## When you should use this

Use this page when the project already has `gdtest`, `gdhealth`, product config
files, CI files, or older docs wording that predates the current suite-first
model.

## What you need before starting

- A repository that already exists
- A committed or otherwise recoverable starting point
- Enough familiarity with the project to review config and docs changes

## Step-by-step instructions

1. Start from the project root.

```bash
cd path/to/existing-project
```

2. Run the adoption command. In a project without `gdsuite.toml`, start with
   `gdsuite init`; in a project set up by an older gdsuite, run
   `gdsuite migrate`.

```bash
gdsuite migrate
```

3. Review the resulting config and doc changes.

```bash
git diff -- gdsuite.toml gdtest.toml gdhealth.toml gdtidy.toml README.md docs
```

4. Run the normal suite checks.

```bash
gdsuite check
gdsuite test
gdsuite health
```

## What success looks like

Success means:

- `gdsuite.toml` holds gdsuite's settings and each tool's section:
  `gdtest.toml`, `gdhealth.toml` and `gdtidy.toml` were moved into `[test]`,
  `[health]`, `[lint]` and `[fmt]`, and `gdlintrc`/`gdformatrc` converted
- sections from gdsuite 0.1 are gone
- old `gdtest` and `gdhealth health` commands in docs or CI are rewritten to
  `gdsuite test -- ...` and `gdsuite health`

## Common mistakes

- Keeping a tool file next to a `gdsuite.toml` section for the same tool: the
  file is ignored, and migrate leaves it in place with a warning so you can
  merge the two by hand
- Leaving stale CI wording that still implies a nonexistent `gdsuite ci` command
