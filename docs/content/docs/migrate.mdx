## What this page is for

This page explains how to bring an existing repository onto the current `gdsuite` config and workflow contract.

## When you should use this

Use this page when the project already has `gdtest`, `gdhealth`, product config
files, CI files, or older docs wording that predates the current suite-first
model.

## What you need before starting

- A repository that already exists
- A committed or otherwise recoverable starting point
- Enough familiarity with the project to review config and docs changes

## Step-by-step instructions

1. Start from the project root.

```bash
cd path/to/existing-project
```

2. Run the adoption command.

```bash
gdsuite init
```

3. Review the resulting suite config and any obvious doc changes.

```bash
git diff -- gdsuite.toml README.md docs
```

4. Run the normal suite checks.

```bash
gdsuite check
gdsuite test
gdsuite health
```

## What success looks like

Success means:

- `gdsuite.toml` reflects the current suite contract
- relevant settings from older product configs are imported into `gdsuite.toml`
- obvious old `gdtest` and `gdhealth health` entrypoints in docs or CI are rewritten toward suite entrypoints
- runtime `gdsuite` commands no longer depend on delegated product configs

## Common mistakes

- Treating `migrate` or delegated-config sync as the main adoption path instead of `init`
- Expecting `gdsuite` to keep `gdtest.toml` or `gdhealth.toml` aligned after import
- Leaving stale CI wording that still implies a nonexistent `gdsuite ci` command
