## What this page is for

This page explains the purpose of `gdsuite check`, the suite's default local validation command.

## When you should use this

Use this page when you want fast feedback during normal development or when you need to understand why `check` behaves differently from `test` and `health`.

## What you need before starting

- Resolved local tooling from `gdsuite init` or `gdsuite setup`
- Optional: `gdsuite.toml` if you want to override the built-in suite defaults

## Step-by-step instructions

1. Run the gate.

```bash
gdsuite check
```

2. Fix what it reports. Formatting and some lint problems fix themselves:

```bash
gdsuite fmt
gdsuite lint -- --fix
```

3. Choose the steps in `gdsuite.toml`, if the defaults don't suit you:

```toml
[check]
steps = ["fmt", "lint", "typecheck", "test", "health"]
```

## The steps

| Step | Runs | Fails when |
|---|---|---|
| `fmt` | `gdtidy fmt --check` (changes nothing) | A file is not formatted |
| `lint` | `gdtidy lint` | A lint rule reports a problem |
| `typecheck` | `gdtypecheck` | Godot reports an error |
| `test` | `gdtest` on `default_test_target` | A test fails |
| `health` | `gdhealth health` | gdhealth exits with an error |

The default is `["fmt", "lint", "typecheck", "health"]`: tests are left out
because they take longest; run them with `gdsuite test`, or add `test` to the
steps.

## What success looks like

`check` runs the steps in order and stops at the first one that fails. If
`gdsuite.toml` is missing, it uses the default steps. The local toolchain
still has to exist, so run `gdsuite setup` first.

`gdsuite check --report json` prints the result of every step it ran and saves
it for `gdsuite report`.

## Common mistakes

- Expecting `check` to reformat files: its `fmt` step only checks. Run `gdsuite fmt` to format.
- Forgetting that `health` is a default step: a project whose health report fails the build fails `check` too. Set `[health]` thresholds, or remove `health` from the steps.
